# Phase 1: Finding and Validating an Idea

Every project starts with an idea. The question is not "do I have a good idea" — it's "how do I research whether this idea is worth building, and what should I actually build first?"

This phase teaches you how to find, validate, and scope ideas using research methods instead of guessing.

---

## 1.1 — Finding Ideas

Ideas are everywhere. The skill is recognizing which ones are worth pursuing and filtering out the noise.

### Sources of Ideas

| Source | How to Research It | What to Look For |
|---|---|---|
| Personal frustrations | Ask yourself: "what annoys me daily?" | Real problems you've experienced firsthand |
| Community discussions | Search Reddit, Discord, forums in your niche | Repeated complaints or requests from multiple people |
| Market gaps | Search for "[niche] + tool" and see what's missing | Underserved needs that existing tools ignore |
| Observing others | Watch how people solve problems manually | Manual workarounds that could be automated |
| Existing tools users complain about | Read app store reviews, GitHub issues, Twitter/X threads | What features are missing, what's broken, what's too complex |

### The Research Task for Finding Ideas

**Do this now:** Open a search engine and search for the following patterns, one at a time:

1. `"frustrating" + [your area of interest]` — read what people complain about
2. `"替代" / "alternative" + [type of tool you're considering]` — see what exists and what they say about it
3. `"[niche] + no good tool"` — find gaps where people are struggling

Write down every idea you find. Don't filter yet — just collect.

## 1.2 — Validating Before Building

The most common mistake solo developers make: building the entire product before checking whether anyone wants it. Validation means testing your assumption with the minimum possible effort.

### The Core Question

Before you build anything, answer this: **who is this for, and what specific problem does it solve for them?**

If you can't answer both parts clearly, you need more research before building.

### Validation Methods (Lowest Effort First)

#### Method 1: The Manual Prototype
This is the cheapest validation. Don't write code — simulate what your product would do manually.

- If you're building a scheduling app, offer scheduling manually via email for 5 people
- If you're building a data analysis tool, do the analysis manually for 3 datasets
- If you're building a notification service, send notifications manually for a week

**How to research whether this works:** After one week of manual operation, ask your users directly:
- "Would you pay for this if it were automated?"
- "What's the hardest part of doing this manually?"
- "Would this make your life easier?"

If fewer than 3 people show interest or say they'd pay — your idea needs rethinking. Don't build yet.

#### Method 2: The Landing Page Test
Build a simple page that describes what you're building and what it does. No code behind it — just a description and a way to collect emails or interest.

- Tools like Carrd, Notion, or a simple HTML page work
- Drive traffic: share in relevant communities, post on social media, tell 10 people
- Measure: do people sign up? Do they share it? Do they ask questions?

**Research method:** Track signups and engagement for 2 weeks. If signups are near zero after sharing in at least 3 relevant spaces, the idea needs refinement.

#### Method 3: The Keyword Search Test
Before building, search for what people are already looking for that isn't well-served.

- Use Google Trends for your idea's core concept — is search interest stable or growing?
- Search Reddit and forums: are people asking about solutions for this problem?
- Search for "[problem] tool" — are there existing solutions? If so, what do their reviews say?

**The key insight:** you don't need a completely new idea. You need an idea that solves a real problem for people who are already searching for solutions.

## 1.3 — Scoping: The "What's Actually the One Thing" Rule

A project is never too big — it's over-scoped when you can't describe what the smallest version that delivers value looks like.

### How to Scope Your MVP

**Research method:** Answer these questions in order:

1. **What is the one outcome this project delivers?** Write it in one sentence. (Example: "This tool lets freelance developers find clients who need their exact skill set.")
2. **What is the simplest version of that outcome?** What's the minimum set of features that delivers 80% of the value?
3. **What features am I adding because they're "nice to have"?** List them. Put them in a separate "future" list. The MVP doesn't include them.
4. **What would happen if I shipped the MVP with only the core features?** Would users find it valuable enough to keep using it? Would they tell others?

### The "Next Milestone" Decision

At every point during development, ask: **what is the smallest next thing I can build or research that makes this project more valuable?**

This prevents two common traps:
- **Building features no one asked for** because you're following an internal vision
- **Stalling because the project feels too big** — when in reality, the next small step is all you need

## 1.4 — Pivoting vs. Continuing

At some point you'll realize your project isn't getting traction. That's normal. The skill is recognizing when to pivot and when to keep going.

### Signals to Keep Going
- People are using it (even if it's rough)
- People are asking for help or reporting bugs (engagement matters more than praise)
- You're learning things you can apply to the next version

### Signals to Pivot
- Zero usage after 30 days of being available (if you can share it)
- People tell you "that's not what I need" — listen carefully
- You're the only user and you're not excited about it anymore
- You built it and nobody told you about it after a month of sharing

### How to Research a Pivot
When you detect a signal that it's time to change direction, research the pivot the same way you researched the original idea:
1. What did my users actually use or respond to?
2. What gap did they reveal that I can fill better?
3. What's the smallest experiment I can run to test the new direction?

## Research Task for Phase 1

**Choose one thing to do right now:**

1. If you have an idea — write down the one sentence description of what it does and who it's for. Then research whether people are searching for or complaining about that problem.
2. If you don't have an idea yet — do the search tasks in Section 1.1 for an area you're interested in. Collect 5 idea candidates.
3. If you have a project in progress — identify the smallest next milestone you can ship in the next week. Research what the simplest implementation would look like.

The goal isn't to finish the research. The goal is to take one concrete step that moves you from thinking to acting.
